# anti-scan-govno

Небольшой сервис на Python для управления отдельной таблицей `inet nftguard`: загружает списки сетей, формирует правила nftables и обновляет их по расписанию. Работает на Linux в Docker Compose с `host` networking и `NET_ADMIN`; внешних Python-зависимостей нет.

## Команды тестирования

| Команда | Назначение |
| --- | --- |
| `./tests/sandbox/run.sh` | Обязательный полный набор после изменений кода: Compose, модульные тесты, установка, удаление, задержка после загрузки, IPv4/IPv6-трафик, отчёт покрытия ≥95% |
| `cat coverage-report/coverage.txt` | Посмотреть итог покрытия после полного набора; HTML — `coverage-report/html/index.html` |
| `python3 -m unittest discover -s tests -p 'test_*.py'` | Быстрый запуск модульных тестов; не заменяет полный набор |
| `python3 -m unittest discover -s tests -p 'test_*.py' -k parsing` | Запуск модульных тестов с фильтром по имени |
| `sh -n install.sh && sh -n tests/sandbox/run.sh` | Проверка синтаксиса POSIX shell-скриптов |
| `bash -n uninstall.sh` | Проверка синтаксиса скрипта удаления |
| `python3 tests/check_compose.py` | Проверка обеих Compose-конфигураций и совпадения параметров сервиса |

## Команды запуска и управления

Только по явному запросу пользователя: эти команды запускают сервис в сетевом пространстве хоста и могут изменить его правила nftables.

| Команда | Назначение |
| --- | --- |
| `docker compose up -d --build` | Собрать образ из исходников и запустить сервис |
| `docker compose -f compose.ghcr.yaml up -d` | Запустить сервис из готового образа GHCR |
| `docker compose logs -f nftguard` | Смотреть журнал сервиса |
| `docker compose down` | Остановить сервис; существующая таблица nftables остаётся |

Интеграционные сценарии не входят в unittest discovery. `tests/sandbox/run.sh` запускает проверки установщика, удаления и реального трафика в отдельной Docker-сети; `tests/integration.py` запускается отдельно. Для них нужен Linux-контейнер с исходниками в `/work`; nftables-сценариям нужны `nft` и `CAP_NET_ADMIN` в изолированном сетевом пространстве. `tests/integration.py` обращается к внешним спискам. Не запускать эти сценарии в сетевом пространстве рабочего хоста.

## Границы и инварианты

- Сервис управляет только таблицей `inet nftguard`; не изменять чужие таблицы и политики. Применение правил — проверенной транзакцией, с сохранением прежнего состояния при ошибках.
- Обязательные списки C24Be должны пройти проверку до применения; сбой необязательного AntiScanner не должен блокировать обновление. Сохранять порядок исключений и блокирующих правил, поддержку IPv4/IPv6 и поведение `DRY_RUN`.
- Не применять правила, не запускать установку или удаление на реальном хосте и не обращаться к рабочим серверам без явного запроса. Для проверок использовать изолированное окружение; помнить, что удаление стирает каталог установки.
- Не добавлять в репозиторий реальные адреса серверов, локальный `.env` и содержимое `state/`; в примерах использовать документационные адреса.
- Не выполнять force push, переписывание истории или выпуск релиза без явной команды.

## Публикация изменений и релиз

Коммит и push выполнять только по явной команде пользователя. Использовать Git для коммита и push, `gh` — для работы с GitHub и проверки Actions; при необходимости использовать авторизацию `gh`. Не выполнять force push и не переписывать историю без явной команды.

При команде на коммит и push:

1. Пройти применимые пункты чеклиста выше, проверить `git status --short` и `git diff`; включить в коммит только изменения, относящиеся к задаче, сохранив остальные изменения пользователя.
2. Создать коммит через `git commit` и отправить текущую ветку через `git push`. Если коммит или push не удался, сообщить пользователю команду и ошибку.
3. Через `gh run list` найти запуски для отправленного коммита и через `gh run watch <run-id> --exit-status` дождаться окончания обязательных проверок. Проверить, что они прошли именно для этого коммита.
4. Если проверка не прошла, изучить журнал через `gh run view <run-id> --log-failed`, исправить причину, выполнить локальные проверки, создать и отправить исправляющий коммит и снова дождаться CI. Если исправить или проверить не получается, сообщить пользователю ошибку и состояние задачи; не объявлять её завершённой.

При явной команде на релиз дополнительно:

1. Подготовить версию и секцию `[X.Y.Z] - дата` в `CHANGELOG.md`, пройти чеклист и опубликовать изменения по порядку выше. Создать и отправить тег `vX.Y.Z` только по команде пользователя.

3. Проверить фактическую публикацию `ghcr.io/theillarion/anti-scan-govno:X.Y.Z` через `docker buildx imagetools inspect` и наличие платформ `linux/amd64` и `linux/arm64`. Сообщить версию, результаты тестов и проверки образа. Если исправление, повторный запуск или проверка реестра невозможны, сообщить пользователю конкретную ошибку и не объявлять релиз успешным.
